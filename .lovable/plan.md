## Phase 3 — Data migration order (safest → riskiest)

**Tier 1 — Operational / append-only (move FIRST, low risk, high cost saving):**
- `analytics_events`, `blog_events`, `cta_events`, `tool_launch_events`
- `intelligence_alerts`, `admin_alerts`, `api_runtime_audit_logs`, `auth_anomaly_events`, `feature_audit_logs`, `operator_audit_log`, `telegram_admin_audit`
- `queue_health_snapshots`, `queue_replay_audit`, `queue_archive`, `queue_dead_letter`
- `ai_job_events`, `workflow_events`, `workflow_failures`, `notification_events`
- `capability_cost_ledger`

These have no live FK dependencies into product tables, are write-heavy, and dominate cost. Moving them clears the biggest Lovable Cloud usage. Read paths swap to `supabaseOwned` in admin telemetry queries only.

**Tier 2 — Async/queue state (medium risk, needs worker coordination):**
- `ai_jobs`, `workflow_runs`, `workflow_steps`, `notification_deliveries`
- `telegram_link_tokens`, `generated_exports`

Strategy: pause workers briefly (`OPS_WORKER_ENABLED=false` on Railway), `pg_dump` + restore, repoint workers' Supabase client, resume. ~2 min worker pause; user-facing flows queue normally.

**Tier 3 — Product data (high risk, last):**
- `profiles`, `user_roles`, `subscriptions`, `wallets`, `wallet_transactions`, `payment_orders`, `referrals`, `blog_bookmarks`, `feature_flags`, `feature_flag_overrides`, `rollout_groups`, intake/work/community tables.

Strategy: dual-write window. Edge functions write to **both** old and new for 48h via the existing `safeAnalyticsInsert`-style pattern. Reads switch table-by-table behind a flag (`migration.<table>.read_new`). Rollback = flip flag off.

**Tier 4 — Auth (`auth.users`, `auth.identities`, `auth.sessions`):**
- Under Option A: **not migrated**. Auth stays on Lovable Cloud. JWT `sub` (user UUID) is preserved across all `user_id` references because UUIDs are stable.
